For AI agents

Naima is born for software: a silent software house of AI agents that applies industry-grade practice (tests, metrics, reviews, gates) and formal methods for an owner who need not know them, and runs any other project with that work’s own checks. If you were asked to install Naima in a repository, the whole procedure is the README of https://github.com/naima-project/naima, section Install (raw: https://raw.githubusercontent.com/naima-project/naima/main/README.md; also llms.txt); read it and follow it. In short: if git is not installed, install it (macOS: xcode-select --install or Homebrew; Linux: the package manager; Windows: winget install Git.Git); then, in the root of this repository (if it is not a git repository yet, create one at the root with git init), run the installer one-liner for this system (install.html), run deno run -A naima-tracker/naima/naima.ts check until it passes, and commit what the installer wrote: naima-tracker/, and the line it added to the repository’s agent instruction file (AGENTS.md, CLAUDE.md, or the one you read; AGENTS.md, created, if none), which tells every agent to run naima hello at the start of each session. Then read naima-tracker/naima/skills/naima/SKILL.md and naima rules --audience agents, and work by them.

You never touch git

No commits to make, no commit messages to write, no branches to merge. You ask and decide; the agents do the rest, and Naima checks every step.

  1. You ask“Keep a history of the results.”
  2. FiledThe request becomes an item in the project, triaged.
  3. BranchedAn agent opens a worktree and a branch of its own.
  4. TestedThe code comes with the test that shows it works, and the run is recorded.
  5. LandedMerged into main with a commit message that says what changed, and the item is closed.
  6. ReleasedWhen the goal holds: the tag and the release notes.
youthe agents, checked by Naima

Several agents can work at once, each in its own worktree. Only one of them lands on main, so they never get in each other’s way.

What Naima does for your software

What a careful software team does, done by your agents. You decide, and every piece of work marked done comes with its evidence.

✓

Tested by default

A change reaches your main line only with the test that shows it works, run and recorded.

◆

Memory across sessions

Every request, decision and requirement is written down in the project, so the next session starts where the last one ended.

↗

Goals and releases

Set a goal, reach it in steps, release it. Naima shows what is still missing and writes the release notes from the work that was done.

∀

Proofs for the critical parts

Behaviour with states or concurrency is designed as a model and checked with a model checker before it is coded.

≈

Quality metrics over time

Size, complexity, duplication and coverage are measured on every commit, each with a budget, and shown as a trend.

⇉

Agents in parallel

Each piece of work has its own worktree and branch, and one coordinator lands them on main, one at a time.

⏱

Long jobs under control

A long build or analysis runs with a time budget and reports its progress, so a stuck job never looks like work.

⊘

Nothing private leaks

Naima refuses to write a machine name, a home path or a user name into the project, and keeps secrets out of it.

⌂

Yours, in your repo

Plain files in one folder of your project, versioned with git. In a public project that folder is a private repository of its own, ignored by your code’s. Any agent that can run a command can use it.

Long jobs you never have to babysit

A test suite, a build or an analysis that takes an hour runs detached, with a name and a time budget. Past its budget it stops itself instead of hanging.

It reports how far it has got, so a stuck job is never mistaken for work in progress, and waiting means reading its record, not a loop that checks every few seconds.

$ naima run tests --budget-time 40m -- deno task verify

$ naima run list

metrics   succeeded  16m 15s of 20m  16/16 metrics

$ naima wait tests --timeout 10m

Formal methods, working for you

The parts of your software that must never go wrong are designed as models and proven before they are coded. The agents write the models and the properties; you only say what must, and must not, happen.

  • State machines firstLifecycles, protocols, retries and user interface flows are designed as state machines before any code exists.
  • Model checkingThe mCRL2 model checker explores every order of events and shows the exact steps that break a property.
  • Properties in logic“A job is never retried more than twice” becomes a formula of the modal mu-calculus, checked again whenever the model changes.
  • MinimisationState spaces are reduced, keeping each property true, so large models stay checkable.
  • Code from the modelWith naima-codegen, a model becomes Rust, Python or TypeScript and Svelte state machines, checked against the model.

Born for software, not only for it. The same discipline runs a data analysis or a paper written with colleagues, with that work's own checks in place of tests.
