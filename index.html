For AI agents

Naima is born for software: a silent software house of AI agents that applies industry-grade practice (tests, metrics, reviews, gates) and formal methods for an owner who need not know them, and runs any other project with that work’s own checks. If you were asked to install Naima in a repository, the whole procedure is the README of https://github.com/naima-project/naima, section Install (raw: https://raw.githubusercontent.com/naima-project/naima/main/README.md; also llms.txt); read it and follow it. In short: if git is not installed, install it (macOS: xcode-select --install or Homebrew; Linux: the package manager; Windows: winget install Git.Git); then, in the root of this repository (if it is not a git repository yet, create one at the root with git init), run the installer one-liner for this system (install.html), run deno run -A naima-tracker/naima/naima.ts check until it passes, and commit what the installer wrote: naima-tracker/, and the line it added to the repository’s agent instruction file (AGENTS.md, CLAUDE.md, or the one you read; AGENTS.md, created, if none), which tells every agent to run naima hello at the start of each session. Then read naima-tracker/naima/skills/naima/SKILL.md and naima rules --audience agents, and work by them.

Agents ask you only what a person must answer

An agent left alone asks you which branch to use and whether to commit. Naima's rules already answer those questions. What reaches you is a judgement, a decision, a password or something done by hand. It comes one question at a time with a suggested answer. Your answer is written down for every later session.

Every test in Naima names who proves it. Most are settled by a command whose run is recorded. Some need an agent to use the running program and keep what it saw. The rest are yours to prove. Proofs are ranked:

What counts as proof, strongest first

  1. You tried it and said yes.
  2. A screenshot, a log line or a number with what it is compared to.
  3. The live state, read by a tool.
  4. A comparison before and after the change.
  5. “The code looks right.” On its own this proves nothing.

What you tell the agents stays out of the repository unless you say yes.

The whole project lives in one folder of your repository

Requests, bugs, decisions, goals, meetings and the project's diary are plain files under naima-tracker/. Every session of every agent starts by reading them.

  • Set a goal and Naima lists what still blocks it. The release notes are written from the work that closed it.
  • When several questions wait for you they are gathered into one meeting with an agenda. You decide when it stops.
  • An issue opened on GitHub becomes an item by itself. The person who reported it gets the fix to try before the release.
  • Several agents can work at once on separate branches while one coordinator lands their work.
  • A data analysis or a paper is run the same way, with its own checks in place of tests.

Machine names, home paths and secrets are kept out of the project. Any agent that can run a command can use Naima.

Formal methods, working for you

Tests check the cases somebody thought of. A model checker checks every possible order of events. Naima uses it on the parts that must never go wrong. Think for instance of a payment that is retried, or a screen waiting for a server. The agents write the model and its properties in mCRL2. You say what must happen and what must never happen.

  • State machines first.Behaviour with states is modelled before any of its code is written, one small machine at a time.
  • Model checking.The mCRL2 model checker explores every order of events. When a property fails it shows the exact steps that break it.
  • Properties in logic.“A job is never retried more than twice” becomes a formula of the modal mu-calculus. It is checked again whenever the model changes.
  • Code from the model.naima-codegen turns the model into Rust, Python or TypeScript. A refinement check proves the generated code never takes a step the model forbids.

In an experiment, eight of ten fresh AI agents asked to build a traffic-light controller generated it from a model this way.

Naima checks itself.Its own coordination protocol is modelled in mCRL2 and checked with the model checker. See how →

You never touch git

The agents file the request, branch, test, merge and release. Naima checks each step.

  1. You ask“Keep a history of the results.”
  2. FiledThe request becomes an item in the project, triaged.
  3. BranchedAn agent opens a worktree and a branch of its own.
  4. TestedThe code comes with the test that shows it works, and the run is recorded.
  5. LandedMerged into main with a commit message that says what changed, and the item is closed.
  6. ReleasedWhen the goal holds: the tag and the release notes.
